# LLM Roleplay Service (the SDK): the rules, as its own tests state them

GENERATED by the Maps fixtures in `CalradiaRemembers.Tests/Maps`. Do not edit: every line is lifted from a
test name and a test file's header, so this cannot drift from the behaviour it describes, and a test fails when
this file no longer matches the suite. See `docs/maps/README.md`.

1480 rules across 209 fixtures. A line marked `(not stated as a rule)` is a
test whose name describes a return value or a branch rather than something anyone would
notice; those are shown rather than hidden, because a gap in a specification should be
visible. There are 107 of them. See CLAUDE.md, "What a test is for".

## General

### ActionBenchCatalogTests.cs

_The extraction bench only proves anything if it actually exercises every action. These pure tests pin the corpus's shape: every dispatchable verb has at least one positive case (the coverage contract, and the forcing function that stays red until the corpus is filled), negative cases exist as a first-class part of the bench, and each case is well-formed enough to run (real prose, a real catalog verb, an expectation on the right side)._

- GIVEN the bench, WHEN inspected, THEN every catalog verb has at least three positive phrasings
- GIVEN the bench, WHEN inspected, THEN it carries negative withholding cases
- GIVEN the bench, WHEN inspected, THEN every case is well formed
- GIVEN the focus slice, WHEN inspected, THEN it is a non empty subset whose every id resolves

### ActionBenchReportTests.cs

_The bench report is what a run actually shows the developer, so its arithmetic and its scoreboard must be exact: a wrong tally or a swallowed failure would send tuning at the wrong verb, or hide a broken run behind a clean number. With more than one pass a case is judged by MAJORITY, so these pure tests (synthetic results, no LLM) pin the run tallies, the pass rule, the majority rule, and that the scoreboard surfaces every non-passing case._

- GIVEN a mix of results, WHEN aggregated, THEN each tally is exact
- GIVEN a partial hit, WHEN aggregated, THEN it is not counted as a pass
- GIVEN a case run three times with two passes, WHEN aggregated, THEN the case passes by majority
- GIVEN a solid case and a flaky case, WHEN formatted, THEN only the flaky one is flagged refineable
- GIVEN a case that fails most of its runs, WHEN formatted, THEN it is listed with its pass rate
- GIVEN a report, WHEN formatted, THEN it lists the failing cases and not the passing one
- GIVEN a miss that emitted an event, WHEN formatted, THEN the event is surfaced with the case id
- GIVEN an all pass report, WHEN formatted, THEN it says all cases passed

### ActionBenchScorerTests.cs

_The extraction bench is only as trustworthy as its judge: if the scorer mis-scores, every downstream fidelity number is a lie. These pure tests feed ActionBenchScorer synthetic emitted-action lists (no LLM) and pin exactly what counts as a hit, a miss, a parameter mismatch, a correct withhold, and a false positive, so the bench's verdicts mean what the report claims they mean._

- GIVEN the expected action with matching params, WHEN scored, THEN it is a hit
- GIVEN the expected action absent, WHEN scored, THEN it is a miss
- GIVEN the expected action with a wrong numeric param, WHEN scored, THEN it is a param mismatch
- GIVEN a numeric param off by one, WHEN scored, THEN it is not a hit
- GIVEN a name param with an honorific prefix, WHEN scored, THEN it still hits
- GIVEN a paramless expected action present, WHEN scored, THEN it is a hit
- GIVEN a negative case with the forbidden verb absent, WHEN scored, THEN it is a correct withhold
- GIVEN a negative case with the forbidden verb emitted, WHEN scored, THEN it is a false positive
- GIVEN the expected type in a different case, WHEN scored, THEN it still hits
- GIVEN a two action case with both emitted, WHEN scored, THEN it is a hit
- GIVEN a two action case with only one emitted, WHEN scored, THEN it is a partial hit

### ActionInterpreterContextBuilderTests.cs

_ActionInterpreterContextBuilder projects the live encounter + the NPC profile into the SETTING/PLAYER/YOU digest the PROSE + INTERPRETER action interpreter reads before it writes a memory. It replaces a hardcoded facts string, and the whole point is grounding and calibration: a memory must be anchored to the real place and witnesses, the NPC's own nature must colour it, and the player must be named consistently. The spike's first interpreter, given no player reference, once recorded the player as "the coward" and baked that one-time insult into a permanent memory. These tests pin the properties that guard against that class of rot: the three labelled lines are always present (so the interpreter always gets its digest), a partial context degrades to real clauses and never the word "null" (so a memory is never grounded in a placeholder), the player is a plain label and never an epithet, and each captivity standing reads correctly (so "your prisoner" and "your captor" are never confused, which would invert who did what to whom in the record)._

- GIVEN a full context, WHEN projected, THEN it carries place witness player label regard and npc label
- GIVEN a near empty context, WHEN projected, THEN it returns the three labels without throwing or printing null
- GIVEN a null context, WHEN projected, THEN it still returns the three labels without throwing
- GIVEN a player label, WHEN projected, THEN the player is named by that label and no epithet appears
- GIVEN no player label, WHEN projected, THEN the player is referred to by a neutral label
- GIVEN captive captor and free statuses, WHEN projected, THEN each yields the correct standing phrase
- GIVEN an npc with a trait, WHEN projected, THEN the nature descriptor appears on the you line
- GIVEN a negative regard, WHEN projected, THEN it renders with an explicit minus sign
- GIVEN conversationInProgress true, WHEN projected, THEN the digest states the conversation is already under way
- GIVEN conversationInProgress false, WHEN projected, THEN the digest is identical to the flagless overload
- GIVEN scene stage conclude, WHEN projected, THEN the digest cues end conversation
- GIVEN a mid scene stage, WHEN projected, THEN no conclude cue appears
- GIVEN a committed romantic status, WHEN projected, THEN the bond is stated on the you line
- GIVEN an intimate event in history, WHEN projected, THEN the digest states an intimate history
- GIVEN no romantic bond or history, WHEN projected, THEN no bond clause appears
- GIVEN recent turns, WHEN appended, THEN they follow the digest under a do not re tag header
- GIVEN no recent turns, WHEN appended, THEN the digest is returned untouched

### ActionTagSanitizerTests.cs

_ActionTagSanitizer is the deterministic safety net that drops an [ACTION] whose type is really an [EVENT] TYPE word (first_meeting, intimacy, ...). Both composition paths (integrated/direct and Prose+Interpreter) occasionally emit one as an [ACTION] - a grok format lapse the prompt guard cannot guarantee against - and the game would only refuse it as an unknown verb, leaving noise in the transcript and the log. It runs inside SectionResponseParser so BOTH paths are protected equally (the interpret step is not penalised for a lapse the direct model shares). These tests pin that it strips exactly the event-type words whatever their casing/separators, keeps every real action (including the flow-control end_conversation, which is NOT an event type), and never allocates or drops on the clean common path._

- GIVEN actions that are really event types, WHEN sanitized, THEN they are dropped
- GIVEN real action verbs, WHEN sanitized, THEN they all survive
- GIVEN end conversation, WHEN sanitized, THEN it survives
- GIVEN event type actions in mixed casing and separators, WHEN sanitized, THEN they are still dropped
- GIVEN a mix of real and event type actions, WHEN sanitized, THEN only the real ones remain in order
- GIVEN a clean or empty list, WHEN sanitized, THEN it is returned unchanged

### AuthoredVoiceRecencyTests.cs
